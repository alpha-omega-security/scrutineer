# Exploratory Audits

Triage normally requests a threat model, whose completion queues planned `security-deep-dive` scans. To check for blind spots in that plan, Scrutineer additionally selects one third of eligible triage invocations for one exploratory audit. Selection is a stable hash of the triage scan ID, so restarting the server or replaying a completion callback does not roll the probability again.

An extra audit is eligible only after a successful, full-mode threat-model scan requested by triage has at least one queued, running, or completed planned deep dive in the same scope and group. Manual threat-model runs, failed threat models, diff rescans, and repositories with no planned audits do not schedule extras. The extra uses the active deep-dive skill's model preference and normal turn cap. It shares the planned batch's finding-deduplication group. Automatic redelivery never schedules a second extra, including after failure or cancellation; an operator may explicitly retry the recorded scan.

When a selected root/default-branch threat model names at least one path-like out-of-scope component or directory, a second stable hash assigns half of those selected runs to an adversarial sweep. The child records one sorted, deterministic candidate as its target. Before invoking an agent, the worker confirms that the target remains out of scope in the repository's current threat model and still contains recognized source after path filtering. If either check fails, the scan records and runs a random dig instead. Scoped and non-default-ref threat models use random digs because their reports are not stored as the repository-wide model needed at execution time.

For a random dig, the worker chooses uniformly among distinct directories containing recognized source-file extensions in the filtered checkout. Root-level source is represented by `.`. Selection ignores `.git`, symlink files and directories, documentation-only directories, and paths outside the requested subproject. It also excludes directory trees named `vendor`, `vendored`, `third_party`, `third-party`, `node_modules`, `dist`, `test`, `tests`, `testdata`, `fixtures`, `__tests__`, `example`, and `examples` at any depth, case-insensitively. An adversarial target may use one of those normally avoided source directories when the threat model explicitly names it, subject to the same skill path filters and repository `scan_config.skip` exclusions. A repository without an eligible source directory produces a visible scan error before an agent is invoked. The source-extension list is conservative; extensionless scripts and unlisted languages are not candidates.

Exploratory audits require container execution and a nonempty instruction file matching the selected mode under the active deep-dive skill's `references/` directory. UI-authored skills and disk or Git overrides without that file still run planned audits, but do not enqueue the extra. Host execution through `--no-container` or `host_skills` is incompatible because host agents can reach unauthenticated loopback exports even without a callback token. The worker rechecks runner compatibility before source selection so queued scans cannot silently switch to host execution after a configuration change.

The scan receives the same findings schema and mode-specific instructions instead of the planned-audit procedure. Random digs receive neither the staged threat model nor `scan_config`, recon, or prior scan reports. Adversarial sweeps receive the threat model only to identify and challenge the selected exclusion; they do not receive `scan_config`, recon, or prior reports. The callback token permits only schema validation of the scan's own report; reads and enqueues are blocked. This is context isolation, not a separate network sandbox: the configured runner's normal egress controls still apply. The selected directory, exploration mode, triage lineage, and actual prompt are recorded for inspection. Retries keep an eligible adversarial target or fall back to a recorded random dig if the model or source changed.

Reports must name their limited scope. The ordinary findings parser, fingerprint deduplication, High/Critical revalidation, and subsequent review gates remain unchanged. An exploratory scan is never accepted as the baseline for a later diff scan, and neither mode overrides explicit operator exclusions.
