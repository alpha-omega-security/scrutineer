# Mobile application threat model

## Reference and limits

This is original, source-review guidance informed by the [OWASP Mobile Application Security Verification Standard (MASVS) v2.1.0](https://github.com/OWASP/masvs/tree/v2.1.0), not a reproduction of the standard or a MASVS compliance assessment. Use the tag-pinned control links below as references, alongside CWE definition links where a weakness class applies. Applicability depends on the platform and framework the app actually uses. Source review cannot establish store or MDM configuration, device integrity, backend enforcement outside the checkout, Play or App Store review outcomes or production signing without additional evidence.

## Actors and assets

Distinguish another app on the same device, a malicious or compromised web page loaded in a WebView, a network attacker on hostile Wi-Fi, a malicious link the user taps and a person with brief physical access to an unlocked or backed-up device. Do not silently grant root or jailbreak, a compromised operating system or the signing key. Protect session and refresh tokens, credentials, cryptographic keys, personal data, the app's privileged actions and the user's backend account.

Inventory each relevant boundary as an entry point, attacker-controlled value, effective guard chain and effect on an asset. Include manifest and `Info.plist` declarations, entitlements, framework bridges and the platform defaults the pinned target SDK sets. Record anything configured outside the checkout, such as server-side token revocation, store policy or device management, as unavailable evidence rather than treating it as unguarded.

## Local data storage

References: [MASVS-STORAGE-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-STORAGE-1.md), [MASVS-STORAGE-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-STORAGE-2.md), [CWE-312](https://cwe.mitre.org/data/definitions/312.html), [CWE-532](https://cwe.mitre.org/data/definitions/532.html).

Find where tokens, credentials, keys and personal data are written and read back: SharedPreferences, NSUserDefaults, plain files, SQLite databases, logs, the clipboard, screenshots and the app switcher snapshot, external storage and backups. A session token in plaintext preferences, a database or a log line is a finding when another party can reach it. Shared external storage is not open to every app that holds a storage permission: under scoped storage another app reaches media through the matching media permission and another app's downloads or documents through the Storage Access Framework, unless the user has granted that app all-files access (`MANAGE_EXTERNAL_STORAGE`, Android 11 onward), which reads shared files directly. Check the file type, the minimum and target SDK and the permission or user grant a reader would need before treating a file there as exposed. From Android 11 onward other apps cannot read the app-specific directories under `Android/data`, but media files in the directories `getExternalMediaDirs()` returns are indexed by `MediaStore` and readable by an app holding the matching media permission, so treat those as shared media. A backup exposes a file only when the backup includes that file and an attacker can obtain the backup. With `android:allowBackup` enabled and no exclusion rules Android still leaves out `getNoBackupFilesDir()` and the cache directories, so check where the file lives against the backup rules, then state how the attacker reaches the backup (for example `adb backup` on a debuggable build or an extracted device transfer). On iOS check whether the item is written to a location that iCloud or device backup includes. Check that sensitive values land in the Keystore, the Keychain or an encrypted wrapper such as EncryptedSharedPreferences. Check also that the accessibility attribute or key protection fits the data. Data stored in the app's private sandbox on an unrooted device is protected by the operating system, so plaintext there is a weakness only with a stated path such as backup extraction or a debuggable build. A secret kept in the Keystore or the Keychain is a negative result only once its protection fits the threat: a Keychain item with an accessibility class that is not `ThisDeviceOnly`, such as the default `kSecAttrAccessibleWhenUnlocked`, migrates in encrypted backups, so check the accessibility class, whether a backup carries the item and whether an attacker can obtain and restore that backup while the token is still valid or reach the item another way. Whether the device encrypts storage and whether the user locks it are device facts to record as assumptions.

## Cryptography and keys

References: [MASVS-CRYPTO-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-CRYPTO-1.md), [MASVS-CRYPTO-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-CRYPTO-2.md), [CWE-321](https://cwe.mitre.org/data/definitions/321.html), [CWE-327](https://cwe.mitre.org/data/definitions/327.html).

Look for keys, initialization vectors and API secrets compiled into the app, since anyone who downloads the package can extract them. Check which primitives protect user data: ECB mode, a fixed or reused IV, unsalted fast hashes for passwords, a non-cryptographic generator such as `java.util.Random`, `Math.random` or C `rand` used where unpredictability matters (`SecureRandom`, `SecRandomCopyBytes` and `arc4random` are cryptographically secure) and custom ciphers. A key derived from public values such as a device identifier protects nothing. Trace where a key is generated, stored and used, then whether it is a hardware-backed non-exportable key. A client identifier or public key that the backend treats as non-secret is a design property. Whether a backend key is truly secret server-side is an assumption.

## Authentication and sessions

References: [MASVS-AUTH-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-AUTH-1.md), [MASVS-AUTH-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-AUTH-2.md), [MASVS-AUTH-3](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-AUTH-3.md), [CWE-287](https://cwe.mitre.org/data/definitions/287.html), [CWE-613](https://cwe.mitre.org/data/definitions/613.html).

Trace how the app decides a user is authenticated and what that decision protects. A check that exists only in the client, such as a boolean in preferences that unlocks a screen or an offline PIN compared in app code guarding data that the backend serves anyway, cannot protect a server resource. A biometric prompt whose result is a callback boolean and is not bound to a Keystore or Keychain key use gates only the user interface for an attacker who can run code in the process, so record that as a weakness where it protects stored secrets and as a design property where it is a convenience lock. Check that logout clears tokens and invalidates the refresh token with the backend call visible in the checkout, that tokens expire and that step-up checks guard sensitive actions. Backend enforcement, token lifetimes set on the server and account lockout are assumptions unless the server is in scope.

## Network communication

References: [MASVS-NETWORK-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-NETWORK-1.md), [MASVS-NETWORK-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-NETWORK-2.md), [CWE-319](https://cwe.mitre.org/data/definitions/319.html), [CWE-295](https://cwe.mitre.org/data/definitions/295.html).

Check what transport the app uses for sensitive traffic. Cleartext is enabled by `usesCleartextTraffic`, `cleartextTrafficPermitted` in `network_security_config` or `NSAppTransportSecurity` exceptions such as `NSAllowsArbitraryLoads`. A scoped exception for a named development host is lower risk than a global one, so read the domain and build variant. Certificate trust is a separate property: a `network_security_config` that trusts user-added certificate authorities in release builds widens which certificates HTTPS accepts but does not permit cleartext, so assess it under certificate validation. Treat a custom `TrustManager`, `HostnameVerifier` or URLSession delegate that accepts any certificate as a finding when it carries session data, since a network attacker can then impersonate the server. The absence of certificate pinning is hardening, not a finding on its own. Whether a debug-only configuration ships in release depends on the build setup, so cite the variant evidence.

## Platform interaction

References: [MASVS-PLATFORM-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PLATFORM-1.md), [MASVS-PLATFORM-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PLATFORM-2.md), [MASVS-PLATFORM-3](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PLATFORM-3.md), [CWE-926](https://cwe.mitre.org/data/definitions/926.html), [CWE-927](https://cwe.mitre.org/data/definitions/927.html), [CWE-939](https://cwe.mitre.org/data/definitions/939.html).

Enumerate every component another app or a link can reach: exported activities, services, receivers and providers (explicit `android:exported` or an intent filter), permissions guarding them, deep links, app links and universal links, custom URL schemes and extension entry points. For each, trace the intent extras, URI or query parameters into the action taken. A finding needs an exported entry that reaches a privileged effect without a permission or caller check, such as loading an attacker URL in a privileged WebView, changing account state or returning private data. Look for intent redirection (forwarding a received intent or an `Intent` extra to `startActivity`), mutable `PendingIntent` objects with implicit base intents, FileProvider path configuration that exposes whole directories, content providers that accept arbitrary selection arguments and task hijacking through `taskAffinity` or `launchMode`. A custom scheme can be claimed by any app, so it cannot authenticate a caller. An app link verified by the domain's asset file is stronger, but the file lives outside the checkout. An exported entry that only opens a public screen is a design property. Read-only handlers that validate the input and perform no privileged action are negative results.

## WebViews and embedded content

References: [MASVS-PLATFORM-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PLATFORM-2.md), [CWE-749](https://cwe.mitre.org/data/definitions/749.html), [CWE-79](https://cwe.mitre.org/data/definitions/79.html), [CWE-346](https://cwe.mitre.org/data/definitions/346.html).

Identify each WebView and what loads into it. A page the attacker controls reaches the app's capabilities through whatever the WebView exposes: `addJavascriptInterface`, `WKScriptMessageHandler` or the React Native, Capacitor and Cordova bridges. Trace the URL source (a deep link parameter, an intent extra, a server field) to `loadUrl`, `load` or navigation, then the enabled settings (JavaScript, file access from file URLs, universal access, mixed content) and the bridge surface reachable from that origin. The finding is attacker-influenced content in a WebView with a bridge that returns secrets or performs privileged actions and no origin allowlist. A WebView that loads only the app's bundled assets or a strict https host allowlist, enforced by comparing the parsed scheme and host rather than a substring, with no bridge is a negative result. A bridge method that exposes nothing sensitive is a design property. Host or subdomain trust that depends on a domain the project does not control is an assumption.

## Code and dependencies

References: [MASVS-CODE-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-CODE-1.md), [MASVS-CODE-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-CODE-2.md), [MASVS-CODE-3](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-CODE-3.md), [MASVS-CODE-4](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-CODE-4.md), [CWE-502](https://cwe.mitre.org/data/definitions/502.html), [CWE-494](https://cwe.mitre.org/data/definitions/494.html), [CWE-1104](https://cwe.mitre.org/data/definitions/1104.html).

Check what the app deserializes or loads: Serializable or Parcelable intent extras read without a type check, Java or Swift archive decoding of attacker data and code downloaded and executed at runtime (`DexClassLoader`, `dlopen` on a downloaded library or a JavaScript bundle fetched over an unauthenticated channel). Verify that downloaded code is integrity checked against a key the attacker does not hold. A dependency with a known flaw is a finding only when the checkout shows the vulnerable function is reachable from attacker input, because a version number alone does not establish exposure. A debuggable flag or leftover test activity in a release variant is a configuration fact tied to the build, so cite the variant evidence. Memory-safety review of first-party NDK or unsafe Rust code belongs to `audit-memory`.

## Privacy and resilience boundaries

References: [MASVS-PRIVACY-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PRIVACY-1.md), [MASVS-PRIVACY-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PRIVACY-2.md), [MASVS-PRIVACY-3](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PRIVACY-3.md), [MASVS-PRIVACY-4](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-PRIVACY-4.md), [MASVS-RESILIENCE-1](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-RESILIENCE-1.md), [MASVS-RESILIENCE-2](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-RESILIENCE-2.md), [MASVS-RESILIENCE-3](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-RESILIENCE-3.md), [MASVS-RESILIENCE-4](https://github.com/OWASP/masvs/blob/v2.1.0/controls/MASVS-RESILIENCE-4.md).

Privacy findings need source evidence of personal data leaving the device or being exposed to another party in a way the app's own declarations contradict, such as an identifier sent to a third-party SDK endpoint the policy denies. Whether a data practice is lawful or matches the store privacy label is outside this audit. Anti-tampering, obfuscation, root or jailbreak detection, debugger detection and certificate pinning are hardening. Their absence is not a finding on its own. MASVS-RESILIENCE is out of scope unless the project states a resilience goal that the code violates. Record the missing evidence as an assumption instead of scoring it.

## Evidence discipline

Every vulnerability needs a reachable first-party source-to-effect path from an attacker position that can occur on a real device and a concrete security consequence under stated prerequisites. Record checked enforcement points as negative results, intentional semantics as design properties and anything that needs store, MDM, device, backend or signing evidence as an unverified assumption. Static review establishes a source argument, not an executed reproduction, a MASVS compliance result or device testing.
